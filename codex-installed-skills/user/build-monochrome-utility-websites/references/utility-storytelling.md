# Utility Product Storytelling

Use this reference to make a product website explain a real tool instead of presenting generic SaaS decoration.

## Start from the first successful outcome

Define:

1. The job the user arrives to do.
2. The moment the product proves value.
3. The shortest path between arrival and that moment.
4. The anxiety that could block adoption.
5. The proof that resolves that anxiety.

Use these answers to order the page. Do not begin with a feature inventory.

## Recommended narrative

### Hero: show the outcome

- State the outcome in concrete language.
- Pair it with a live-looking interface state that demonstrates the core utility.
- Use a short subhead that explains who it serves and why it is better.
- Offer a primary action and, only when useful, a lower-commitment secondary action.

### Proof: remove the first doubt

Use one of:

- Credible performance numbers with definitions.
- Supplied customer logos or quotes.
- A concise reliability, security, or compatibility statement.
- A before/after workflow comparison.

Never invent endorsements, metrics, or security certifications.

### How it works: make the system legible

- Use three or four steps maximum.
- Give each step a visible product state, not an abstract illustration.
- Keep verbs parallel: Schedule → Join → Collaborate → Follow up.
- Use progressive disclosure for implementation details.

### Capabilities: group by user goal

Group features by outcomes such as “Stay present,” “Capture decisions,” or “Bring everyone in.” Avoid grouping only by internal architecture.

### Use cases: vary the context

Show a few distinct situations. Change participants, content, or workflow, not merely the heading above the same card.

### Trust: address adoption friction

Place security, privacy, reliability, integrations, accessibility, or support where the user starts asking about risk. Link to deeper documentation when available.

### Final action: repeat the promise

Summarize the outcome in new words and offer one decisive CTA. Do not turn the footer into another full landing page.

## Zoom-like and collaboration products

Demonstrate at least three relevant states across the page:

- Pre-session: scheduling, room setup, device check, invite, or agenda.
- Live session: participant presence, audio/video controls, screen share, chat, reactions, or collaborative canvas.
- Post-session: recording, transcript, decisions, highlights, tasks, follow-up, or analytics.

Make the UI understandable without relying on brand familiarity. Use conventional symbols and labels for high-frequency controls. Represent participant diversity respectfully and avoid uncanny generated headshots when simple initials, user-supplied photography, or abstract avatars are sufficient.

## Product-demo composition

- Build the demo from actual semantic elements when interaction matters; use static artwork only when clearly decorative.
- Limit the visible control set to what supports the story.
- Reveal secondary detail on deliberate interaction or scroll, not all at once.
- Use scale, crop, and layering to direct attention to the active state.
- Use credible copy. “Quarterly planning,” “Design review,” and “3 action items” communicate more than lorem ipsum.
- Mark simulated data or disabled controls when users might mistake the marketing demo for a working product.

## Copy style

- Lead with strong verbs and plain nouns.
- Prefer “Start a clear meeting in one click” to “Reimagine seamless collaboration.”
- Keep headlines short enough to form intentional line breaks.
- Use supporting copy to explain mechanism or proof, not repeat the headline.
- Give buttons specific labels such as “Start a room,” “Watch the demo,” or “See the transcript.”
